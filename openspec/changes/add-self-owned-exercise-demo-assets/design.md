## Context

动作库当前由 `ExerciseLibraryContentView` 统一渲染 browse 与 pick 场景。72pt 左侧媒体区的单列动作行仍不足以清楚展示完整人物和器械，因此右侧动作区改为按既有解剖层级分段的双列小尺寸图卡片：单卡不撑满可用列宽，在当前 iPhone 上最大约 104pt；卡片上部为约 1.25:1 的白色媒体区，方形素材在其中等比完整显示、保留顶部呼吸空间并靠近下方标题，下部为 26pt 起的居中动作名。动作详情页仍另行使用 `MuscleMapView` 展示完整肌群定位。随包 manifest 当前包含 224 个内置动作，并以稳定 `BuiltinExercise.code` 标识。

旧方案试图把 imagegen 静态母版转成 Blender 角色、器械和 12 帧 GIF，实际产物未达到批准静态图的视觉水平，生产链也远超列表缩略图所需。新方案把“高质量静态母版”直接定义为最终美术内容，只做确定性缩放和编码，不再把它重建成 3D 或动画。

此前批准的 `PEC_DECK_FLY` 效果图 1 只作为视觉验收基准：常规顶部横梁式蝴蝶机、中央座椅与靠背、左右弯曲摆臂和垂直握把、45° 视角、统一灰阶解剖人物、胸大肌朱砂红高亮、无文字和 Logo。母版保留原始暖白底作为审计证据，运行时导出必须将其归一为纯白。它不是第三方参考图的派生品，也不能免除新流程中的来源、角色一致性和技术审核。

## Goals / Non-Goals

**Goals：**

- 建立一个可在全部动作中复用、可人工比较的原创统一角色。
- 使用 imagegen 生成高质量单张动作图，并在 288×288 下清楚表达动作、器械和主要目标肌。
- 让已批准图片通过稳定 code 渐进替换动作库现有肌群缩略图，未覆盖条目安全降级。
- 保存跨电脑继续工作所需的母版、brief、来源、审核、脚本和正式资源。
- 用已验证动作锁定一致性、可读性、包体和滚动性能后，按动作族持续覆盖全部内置动作；无法达到标准的条目记录并跳过。

**Non-Goals：**

- 不制作或播放任何动态媒体，不维护 Blender/3D/骨骼/帧序列。
- 不改变动作详情页肌群图、动作数据、训练记录或服务端契约。
- 不以“同一 prompt”代替人物一致性审核；未获项目所有者授权时不得自动批准 AI 结果。
- 不以低质量或动作/器械猜测覆盖全部 224 个动作。

## Decisions

### D1：静态 AI 母版就是最终美术真相源

每个动作只维护一张已批准的高分辨率母版。正式列表图由该母版确定性裁切、合成和缩小，不再经过 Blender 重建，也不生成中间动作帧。

母版至少 1024×1024、sRGB，保留足够细节用于重新导出；运行时统一识别四角相近的烘焙暖色背景并归一为纯白，再导出为 288×288、JPEG 质量 82、不透明纯白背景的 JPG，单张不得超过 24 KiB（24,576 bytes）。当前 402pt 宽 iPhone 的右侧可用区可稳定容纳两张最大约 104pt 宽的卡片；288px 相比旧 144px 明显降低 3x 设备上的放大软化，同时维持可控包体。首个真实列表验收必须检查细线、器械、安全边距、背景色块和快速滚动，不允许逐动作混用标准。

实测 `PEC_DECK_FLY` 同一母版、质量 82：144×144 为 7,787 bytes、216×216 为 13,785 bytes、240×240 为 16,223 bytes；最终纯白背景 288×288 运行时文件为 21,831 bytes。双列紧凑图卡片下 144px 明显不足，288px 在 24 KiB 上限内提供最佳折中；按该样例估算 226 张约 4.7 MiB。备选方案仍是运行时 PNG；若 288px JPG 仍无法通过视觉验收，应在扩量前整体改格式或构图，而不是逐动作混用。

### D2：角色母版与风格母版分离

正式生成依赖两个已批准的自有输入：

1. `character-v1`：同一名原创虚构成年男性的正面、45° 和侧面角色表，锁定脸型、短深色发型、肤色/灰阶、身高体型、四肢比例、黑色训练短裤和无鞋造型；
2. `style-v1`：锁定灰阶医学插画密度、朱砂红主动肌、浅红协同肌、暖白背景、柔和阴影、视角、留白和无文字/Logo 规则。

此前批准的 `PEC_DECK_FLY` 效果图 1 是建立 `style-v1` 和 45° 全身构图的验收基准，但正式 `character-v1` 仍需单独生成并由用户批准。这样后续动作不会把某台器械或某个姿势误当作角色身份的一部分。

### D3：所有动作必须从角色 reference/edit 生成

每个动作的生成调用必须同时提供已批准的角色母版、风格母版和原创动作 brief。brief 只描述当前动作的：

- 稳定 code、中文名、动作变体和代表姿势；
- 相机方向、人物与画布占比、安全边距；
- 器械类别、必须出现的识别特征、握法和身体接触点；
- 关节角度、身体姿态和常见错误排除项；
- 主动肌与协同肌高亮范围。

禁止只复用 seed、角色名称或文本描述来宣称人物一致。imagegen 无法提供数学意义上的身份保证，因此产品保证来自“固定 reference/edit 输入 + 固定身份清单 + 联系表人工对比 + 漂移即拒绝”，而不是模型承诺。

### D4：角色一致性采用可拒绝的验收合同

每张候选图必须与 `character-v1` 和已批准动作联系表并排检查以下项目：

- 面部轮廓、发际线、发型和可见五官没有换人；
- 肩宽、胸腰比、四肢长度、手脚大小和肌肉量处于同一角色范围；
- 服装、肤色/灰阶、线稿密度和阴影语言一致；
- 不存在多余/缺失肢体、手指融合、左右颠倒或不合理关节；
- 角色在 288×288 和真实双列卡片下仍能与已批准图片被识别为同一视觉主体。

任一关键项漂移即拒绝，不允许后期只改文件名或台账状态绕过。连续生成无法稳定收敛时，该动作保持现有肌群缩略图，不降低标准上线。

### D5：动作与器械准确性独立于美术审核

每个动作建立独立 brief 和验收卡。器械动作必须在 288×288 和真实双列卡片下保留能识别其器械类别的结构；自由重量与自重动作只保留说明动作所需的最少环境。动作审核至少检查起始/代表姿势、关节方向、握法、身体接触点、器械类型和目标肌，不用漂亮构图掩盖机械或动作错误。

`PEC_DECK_FLY` 必须使用已批准效果图 1 的常规顶部横梁式蝴蝶机，而不是胸推机、绳索夹胸或左右独立短直臂变体。人物坐姿、背靠、双脚、握把和胸肌高亮必须正确。

### D6：输入与权利边界保持可追溯

正式输入只允许原创文字 brief、本项目自有角色/风格母版，以及明确许可该用途的素材。`hasaneyldrm/exercises-dataset` 图片不得下载入库、作为 image reference/edit 输入、转描源、训练输入或像素级构图模板；其信息只可用于确认动作名称、常规器械部件等通用事实。

每个已批准母版记录工具与模型版本、完整 prompt/brief、全部输入及权利状态、生成日期、人工修改、审核人、审核时间和 SHA-256。实施前必须重新留存当时 imagegen 服务的商业使用条款；AI 生成不自动等于独占、无侵权或动作正确。

### D7：只有已批准资源才能进入运行时 manifest

生产 manifest 以 `BuiltinExercise.code` 为主键，保存角色版本、风格版本、高分辨率母版、运行时文件、来源摘要和五类状态：

- `identity`：角色一致性；
- `art`：构图、线稿、颜色与 288×288/真实卡片可读性；
- `movement`：动作姿势和目标肌；
- `equipment`：器械类别与结构；
- `rights`：输入和工具条款。

五类均由稳定人工主体或经项目所有者明确授权的 `production-autopilot` 批准且自动技术校验通过后，导出脚本才可生成/更新精简运行时 manifest。未获授权时，自动化和 Codex 只能提供候选与证据，不能冒充人工把审核状态改为 `approved`；获授权时必须如实使用 `production-autopilot` 身份。

### D8：列表按 code 加载，失败时沿用现有降级链

未来新增轻量 `ExerciseArtworkLibrary`，只解析随包静态 manifest，并按 code 返回正式 JPG。内置动作行的显示顺序为：

1. 已批准且文件完整的 288×288 实际动作图；
2. 现有 `MuscleMapThumbnail`；
3. 名称首字占位。

browse 与 pick 共用同一 `ExerciseLibraryContentView`，因此共用这一缩略图规则，避免同一动作在两个选择入口显示不同图片。列表只使用 SwiftUI 本地静态 `Image`，不做网络请求、不解码动画、不预载高分辨率母版。图片作为装饰隐藏于 VoiceOver，动作行原有名称和副标继续承担可访问语义。

右侧动作区使用两列 `LazyVGrid`，每个分段 header 横跨网格宽度，卡片保持稳定 code/UUID identity。两列使用 88–104pt 的受限弹性宽度并在右侧内容区居中，不再撑满可用列宽；正式动作图、肌群降级图和首字占位占据同一个约 1.25:1 的白色媒体区。方形素材使用 `scaledToFit`，在媒体区底部保留 4pt 间距，使顶部留白大于底部留白、主体更靠近标题；正式动作图保留基础边距，肌群降级图使用更大的安全边距，避免局部肌群贴边放大。旧肌群 PNG 中与四角背景相近的像素确定性转为透明，正式 JPG 的相近暖色背景确定性归一为纯白，因此图片区域不再出现独立粉色方块。动作名置于最低 26pt 的卡片底部并从顶部开始排版，使用 12pt 字号，允许两行并保持卡片等高；更短的标题区同步缩小单行动作名到底边的留白，把卡片主要空间留给动作图。卡片整体是单一点击目标并承担 VoiceOver 语义，装饰图片隐藏；browse/search/pick、自定义动作长按删除、器械快速索引和分页行为保持不变。卡片沿用现有纸感、朱砂红、边框与圆角，媒体和卡片底色保持白色，不引入参考产品的蓝色或“讲解”角标。

### D9：先锁定标准，再按动作族自治覆盖全量

第一道闸门只处理 `PEC_DECK_FLY`，在真实双列卡片中批准角色、蝴蝶机、动作、肌肉高亮和 288×288 效果。通过后制作 12 个覆盖不同难点的代表动作：

`PEC_DECK_FLY`、`BB_BENCH_PRESS`、`BB_SQUAT`、`DEADLIFT`、`OHP`、`BB_ROW`、`LAT_PULLDOWN`、`LATERAL_RAISE`、`DB_CURL`、`TRICEP_PUSHDOWN`、`LUNGE`、`PLANK`。

已完成的代表动作以联系表验证角色没有逐张漂移，并测量 App 包体、列表首次加载、快速滚动和内存。项目所有者已授权后续按相同标准自治覆盖其余内置动作：每个动作仍须经过五类审核、确定性导出和技术校验；无法确定唯一动作/器械标准或无法稳定达标者写入跳过台账，未覆盖动作继续使用旧缩略图，不生成低质量占位。

### D10：版本控制只保存继续工作所需的资产

未来目录边界：

```text
art/exercise-static/
├── references/approved/     # character/style 母版与对应 prompt/brief
├── masters/approved/        # 已批准高分辨率动作母版
├── briefs/                  # 动作与器械验收卡
├── manifests/               # 生产 manifest、schema 与来源台账
├── scripts/                 # 导出、校验、promote、联系表脚本
├── reviews/                 # 人工审核记录和条款证据
└── staging/                 # 候选与失败图，仅本地，Git 忽略

ios/DontLift/DontLift/Resources/ExerciseArtwork/
├── exercise_artwork_manifest_v1.json
└── exercise_<CODE>.jpg
```

已批准高分辨率母版若实测较大，使用只匹配 `art/exercise-static/masters/approved/**` 和角色/风格母版的 Git LFS；288×288 运行时 JPG、JSON、Markdown 和脚本使用普通 Git。fresh clone 必须能取得所有已批准输入、重新导出相同尺寸和质量的 JPG 并在不安装 AI 工具时完成 iOS 构建。API key、账户凭证、候选图和缓存不得入库。

### D11：不引入服务端数据模型

静态 manifest 和图片是随 App 发布的只读资源，不是用户数据，也不参与同步。因此本 change 不新增后端实体，不适用身份三层、写接口幂等键、同步字段或软删除；现有 Day-1 数据铁律保持不变。若未来引入远程素材管理，必须另起 change 重新设计这些边界。

## Risks / Trade-offs

- **角色仍可能漂移** → 每次必须 reference/edit 生成并与角色母版、联系表逐项对比；不收敛就不发布该动作。
- **静态代表姿势不能说明完整轨迹** → brief 选择最能表达器械、方向和发力的姿势，同时保留动作名称与详情要点；本 change 不伪装成完整教学动画。
- **AI 可能生成动作或器械错误** → 将 identity、movement、equipment 分开自治或人工审核；无法可靠收敛的条目写入跳过台账，不阻塞其他动作族。
- **医学插画可能被误解为精确解剖图** → 目标是动作识别和目标肌提示，必须人工复核，不在 UI 宣称医疗或康复指导。
- **高分辨率母版增加仓库成本** → 只保存已批准母版，候选不入库；实测后使用路径限定 Git LFS。
- **JPG 压缩损伤细线** → 在 288×288、质量 82、≤24 KiB 条件下做真机审核；失败则重新构图或在扩量前整体改格式，不对单个动作放宽规则。
- **部分动作有图、部分无图会不一致** → 以质量优先的渐进替换为明确产品状态，旧肌群图作为稳定降级，不使用劣质占位凑齐。

## Migration Plan

1. 删除旧 Blender/GIF 实施产物和配置，仅保留重写后的 OpenSpec 工件。
2. 实施获批后，先创建并批准 `character-v1`、`style-v1`、schema 与来源台账。
3. 重新生成/整理 `PEC_DECK_FLY` 正式高分辨率母版，完成五类人工审核并导出 288×288 JPG。
4. 在真实动作库双列卡片接入静态 manifest 和三级降级，验证无图条目行为不变。
5. 通过首道闸门后补齐代表动作，完成联系表、包体和滚动性能验收。
6. 按项目所有者授权的自治策略扩展剩余内置动作；每个动作只在通过审核后发布，或记录为已跳过。

回滚只需删除运行时 manifest 条目和对应 JPG；列表立即回到现有肌群缩略图/首字链路，不涉及数据迁移。已批准源文件与审核历史保留，便于修订。

## Open Questions
