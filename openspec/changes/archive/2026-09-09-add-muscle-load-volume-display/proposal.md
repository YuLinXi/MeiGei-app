# 肌群负荷展示容量

## Why

肌群负荷的数据层（`MuscleLoadAggregator`）早已按既有 `statEntries` 口径算出肌群桶级容量（`MuscleLoadEntry.volumeKg`），但 UI 层只展示有效组数：首页小卡与周复盘页的共用行组件 `MuscleLoadRowView` 只渲染「N 组」，容量只在复盘页两级下钻后的动作级贡献明细里出现。用户无法在负荷板层面感知各肌群的训练容量，而这恰是衡量肌群刺激量的关键指标。

此外，现行规格「周复盘页与同期对比」（`workout-tracking/spec.md`）本就要求每个肌群条目「同时展示训练量数字」，实现侧遗漏了——本次一并补齐该规格缺口。

## What Changes

- `MuscleLoadRowView`（首页小卡与周复盘页共用的肌群行组件）在组数之后同排展示容量，格式为「12 组 · 8.6 t」，容量以弱化色作为参考值，组数仍为视觉主数字。
- 首页「本周肌群负荷」小卡的 Top3 条目随共用组件一并获得容量展示。
- 周复盘页全部肌群条目（含为 0 的肌群，容量按格式化结果照常展示）获得容量展示。
- 周复盘页头部总览从「共 N 有效组」扩展为「共 N 有效组 · 总容量」。
- 周复盘页头部同期对比文案从纯组数扩展为组数 + 容量双分量（如「较上周少 2 组 · 多 0.9 t」）；某分量持平（变化为 0）时不展示该分量文字，两个分量均持平时整条对比文案不展示。
- **对比基线口径调整**：本周视图的对比基准从「上周同期（按已流逝时长截断）」改为「上周整周」——避免「本周 42 组 vs 上周 44 组却显示多 29 组」这类用户可对账的矛盾感；文案只说「较上周」，不出现「全周」「同期」字样。
- 上周视图改为纯数据回看：头部与展开面板均不展示任何对比文案（不再对比上上周），聚合层 `previousBaseline` 与 `sameOffsetPreviousWeekRange` 随之移除。
- 肌群条目内**移除**变化胶囊（+N 组 / 持平 pill）；同期对比详情下沉到点按展开的贡献明细面板，包含该肌群的组数变化与容量变化。
- 容量格式化复用既有 `formatMuscleLoadVolume`：≥1000 kg 显示吨（如 8.6 t），否则整数 kg。
- 排序键与近 4 周趋势柱**保持组数口径不变**。
- 数据层仅新增 `MuscleLoadAggregator.volumeKg(of:in:)` 取值入口（与既有 `sets(of:in:)` 同构），聚合口径零改动；`volumeKg` 已在 `MuscleLoadEntry` 现成，本次为 UI 展示层变更。

## Capabilities

### New Capabilities

（无）

### Modified Capabilities

- `workout-tracking`: 修改「首页肌群负荷小卡」与「周复盘页与同期对比」两条需求——肌群条目在有效组数之外同排展示容量（首页小卡为新增要求；复盘页条目为补齐规格中已有「同时展示训练量数字」的实现缺口并明确展示形式）。排序、同期对比、近 4 周趋势口径明确保持按有效组数。

## Non-goals

- 不改变肌群负荷的聚合口径、周界、归组规则（沿用 `countsForStats` / `statEntries` / 两段式归组）。
- 不把容量引入排序键与近 4 周趋势柱——这两项维持有效组数口径。
- 不在首页小卡底部摘要追加总容量（总容量只出现在复盘页头部）。
- 贡献明细的动作级列表维持现状（组数 + 容量已实现），仅在其上方新增肌群级对比详情行。
- 不涉及后端、同步协议与持久化变更。

## Impact

- **代码**：`ios/DontLift/DontLift/Workout/MuscleLoadReviewView.swift` 中的 `MuscleLoadRowView`（共用组件，改一处两处生效）；首页小卡调用点（`WorkoutViews.swift` 的 `muscleLoadSection`）可能需微调布局参数。
- **规格**：`openspec/specs/workout-tracking/spec.md` 的「首页肌群负荷小卡」「周复盘页与同期对比」两条需求。
- **测试**：聚合层无变化，无需新增单元测试；UI 层以真机目检为主。
- **无后端 / API / 数据库 / 同步影响**，纯客户端展示层变更，向后兼容。
