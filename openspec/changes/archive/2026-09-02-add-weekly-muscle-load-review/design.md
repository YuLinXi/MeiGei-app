## Context

现状（见 proposal.md - Why）：

- 统计口径已有单一事实源：`WorkoutSet.countsForStats`（已完成且非热身）、`statEntries`（递减组 segments 展开）；周界有 `WorkoutWeeklyStats.weekBounds`（本地时区周一 00:00）。
- 肌群体系：`ExerciseCategory` 八个解剖类 L1（中文 rawValue）+ 三个非解剖类；`WorkoutExercise.primaryMuscle` 在创建训练时已快照；`historyKey` 规范合并（builtinCode ?? customId ?? name）已用于曲线/PR。
- 首页 hero 与周聚合均为「即时重算、不入库」；`WorkoutHistoryStore` 持有内存训练集。
- 无任何持久化聚合表，本 change 亦不引入。

## Goals / Non-Goals

**Goals:**

- 一个纯函数聚合层：任意 `[start, end)` 区间 → 八肌群 + 「其他」的组数/训练量（为周板、同期对比、4 周趋势共用）。
- 首页小卡 + 独立复盘页两级呈现；复盘页含近 4 周迷你趋势与贡献明细。
- 全部单元测试可覆盖，页面层薄。

**Non-Goals:**

- 不做计划覆盖对比、参考区间、自然月/滚动 7 天等其它维度（见 proposal Non-goals）。
- 不引入图表库；趋势用自绘轻量组件。

## Decisions

### D1: 聚合层为区间参数化的纯函数，维度扩展零成本

`MuscleLoadAggregator.load(workouts:in:)` 输入训练集与区间，输出 `[MuscleLoadEntry]`（肌群、有效组数、训练量）。周板传本周区间、同期对比传上周截断区间、趋势传 4 个自然周区间分别调用。未来若加月视图/滚动 7 天，只是调用方换区间，聚合层不动。

- 备选：按周固化的专用函数 → 拒绝，会把「同期截断」「4 周序列」逼成特判。

### D2: 同期对比用「上周同一周内偏移」截断

周中看数时，本周 N 天对比上周全 7 天必然显得欠练。统一取上周 [周一, 周一+N天) 作为对比基准，保证公平；切换到完整周（上一周）时基准为上上周同偏移。

### D3: 归组两段式，快照优先

动作肌群归属以训练创建时的 `primaryMuscle` 快照为准（历史不受后续动作库改名/调整影响）；快照为 nil 的老数据回退 `ExerciseLibrary` 按 `historyKey` 解析。`primaryMuscle` 存的是 L1 rawValue（如「胸」），直接映射 `ExerciseCategory`；映射失败进「其他」。归组逻辑收在聚合层，单元测试锁定。

### D4: 趋势用自绘 sparkline，不引图表库

每肌群近 4 个自然周组数序列 → 归一化折线/柱状迷你图（约 48×20pt）。Swift Charts 引入为单个迷你图过重；自绘 `Canvas`/`Path` 组件足够，且与纸感体系易对齐。全 0 序列绘制基线而非空图。

### D5: 首页小卡与复盘页复用同一条目组件

小卡取负荷 Top 3-4 复用复盘页的肌群条目组件（条形 + 组数 + 变化），避免两处版式漂移；复盘页额外挂趋势 sparkline 与「其他」桶。小卡空态与 hero 空态文案风格对齐。

### D6: 明细为复盘页内下钻，不新增独立页面

点按肌群在复盘页内展开/跳转明细区（动作名、组数、训练量，降序）。数据由同一聚合层按肌群过滤派生，无新数据流。

## Risks / Trade-offs

- [「其他」桶因老数据快照缺失或自定义动作未填肌群而偏大，稀释可信度] → 归组两段式兜底；实现后先用真实数据跑一次分布验证（占比高则在明细页可见原因），必要时再补手动归类。
- [周中条形普遍偏短，视觉上像「欠练」引发误解] → 同期对比口径（D2）保证对比公平；小卡与复盘页文案注明「较上周同期」。
- [近 4 周趋势与历史曲线（动作级）视觉语言不一致] → 趋势组件刻意极简（无轴无数值，仅方向），与动作详情页带轴曲线拉开层级。
- [首页再增一卡加重首屏] → 小卡克制为 Top 3-4 条 + 摘要行；零训练时收敛为空态文案而非空图。

## Migration Plan

纯客户端增量：无后端、无迁移、无同步变更。随 v1.1-b3（或下一候选）正常发版即可；旧版本客户端不受影响。
