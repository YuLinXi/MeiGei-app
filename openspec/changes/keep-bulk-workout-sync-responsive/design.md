# Design

## Context

动机见 proposal。现有 `SyncEngine` 在主执行器上维护与 UI 共享的本地模型；HTTP 与 JSON 编解码由独立网络 actor 处理。原生栈已确认逐条根查询会遍历大量待保存子节点。批量查找修正后，5000 条、每条 6 动作×4 组的 SQLite 恢复仍有约 14 秒的主执行器调度空档，后续工作须同时约束应用与保存阶段。

现有可靠性边界来自 `harden-session-save-sync-recovery`：本地修改保护、毫秒回声容差、保存成功后提交水位、会话代数以及单域失败不阻止其他域。分批执行不能削弱这些保证。

## Goals / Non-Goals

**Goals:**

- 减少重复根查询，按完整训练子树的规模形成有限本地提交批次。
- 在批次之间允许主执行器处理输入与会话变化；中断后能安全停止或重放。
- 对真实 SQLite 写入、保存失败后恢复、未推送编辑和会话清理提供定向证据。

**Non-Goals:**

不改变同步协议、schema、统计口径或 Team 权限，不引入通用作业队列。组件调度采样不能替代可见帧、真机或能耗门禁。

## Decisions

### 1. 在有界窗口内批量取得已有根对象

按最多 32 个下拉聚合的 `localId` 查询本地根对象，以短生命周期索引供当前窗口使用；新插入的根也加入索引以保持同窗口身份一致。进入下一窗口前可靠保存当前窗口残余并让出主执行器、核验周期，因此下一次查询不会扫描尚未提交的大批子树。索引不跨窗口或周期保存；重复 id 在后续窗口按同一本地身份重新取得。

最初一次查询全部响应已消除逐条查询的重复遍历，但 5000 条已有子树更新仍有约 199.5ms 的调度空档。保存分段最高约 57.6ms，原生栈另记录到整批根查询／物化阶段；进一步限制查询窗口，以避免该阶段成为剩余的长主线程任务。两种候选的样本分别保留。

### 2. 按子树规模控制提交批次

按约 128 个变更模型节点形成批次，节点计数包含根、新动作和新组；更新或删除时也计入将移除的旧动作与组。在加入下一棵树会超出预算时，先保存前一批、让出主执行器并核验会话，再应用下一棵树；完整聚合不拆分。最后一个批次由周期最终保存收口。具体上限随同口径调度采样校准，不作为用户配置或持久化字段。

最初 256 节点候选的标准恢复矩阵已完成，5000 条的最长调度间隔最大 114.1ms。已有子树更新补测中，单次保存最高约 91.1ms；只计新节点低估了删除旧子树的工作。因此补齐删除成本并降低预算，保留最初候选与新候选的独立样本，不将历史结果套到新候选。

仅在整批循环中增加让出操作仍会把全部新增子树留给最终的大保存；因此需要同时减少单次提交规模。共享 context 的现有身份、编辑和冲突保护保持原样；若后续证据表明该方案仍不满足要求，再按实际热点调整内部执行方式。

### 3. 周期保存失败是持续到收尾的结果

域执行结果携带服务端水位与本地批次保存失败标志。本地批次失败即终止该域后续应用，其他域仍按现有规则收口；即使最终保存随后成功，本轮仍按本地保存未完整成功处理，全部待提交水位保持原值，也不发布可靠训练同步成功事件。部分已经提交的聚合保留在库中，下次按相同身份重放。

保存通过一个默认调用现有 context 保存的方法入口执行；定向测试可注入一次真实保存前失败、随后恢复的提交函数，验证最终保存成功不能掩盖中途失败。该入口不负责重试、排队或数据迁移。

### 4. 每次批次挂起后重新核验周期

每次让出主执行器之后，先校验代数、会话和取消状态，再读取索引中的模型或继续保存。用户在批次之间编辑模型后，后续应用仍检查当前待推送状态；缓存的只是当前模型身份，不是其旧字段快照。

墓碑交错回归确认，原先先删墓碑再检查待推送状态会删除批次间刚保存的输入。因此训练下拉统一先保护待推送模型，再处理墓碑或较新子树；已同步模型仍接受墓碑并清理子树。待推送项继续交给后续 push 的既有 LWW 与冲突反馈，不在客户端额外合并。

### 5. 数据模型与接口保持原状

业务归属继续通过既有用户与提供方身份分离处理；不改 JWT 或 Keychain。`localId/serverId/updatedAt/deletedAt/version/syncStatus`、训练子树主外键、墓碑及 LWW 原样保留。HTTP push 幂等键不变，本地分批不成为新的远端同步实体；CloudKit 继续关闭。

### 6. 模型字段复制与写入串行，后台仅处理值

实际 5000 条已有子树更新 UI 回归触发 `BadgeHistoryReader` 在读取 `WorkoutExercise.orderIndex` 时发生 SwiftData backing data 失效断言。64 条 SQLite 数据、反复同步替换与两类读取器的缩小用例连续两次复现；每轮新建读取器仍崩溃，说明读取器自己的 ModelActor 不能阻止另一个 context 删除其尚在读取的子节点。

使用专用于训练快照的 `WorkoutSnapshotCapture`：在主执行器上取得持久化标识，按小窗口用新只读 context 同步复制完整聚合，窗口间只保留标识与 Sendable 值并让出执行器。标识查询保留原顺序；已在两个窗口之间删除的根跳过，取消在每个窗口核验。模型字段访问和当前全部训练写入由同一执行器串行，避免复制期间关系被替换；不引入全局锁或阻塞主线程等待后台读者。

原历史与勋章读取器改为值入口，不再持有独立 ModelActor 的 live 模型。别名解析、派生统计与批量值变换沿用现有执行位置；较重聚合仍在后台。异步 signpost 覆盖整个字段复制阶段，不用一次小窗口的耗时冒充全量读取耗时。该策略必须复测大历史下的输入与快照吞吐，不能用修复崩溃替代性能验收。

## Risks / Trade-offs

- [更多本地事务增加吞吐成本] → 同设备、同 SQLite 数据结构比较总耗时及每轮最长调度间隔；同时记录 CPU／帧边界，不只挑一次最快结果。
- [挂起后旧模型已经清理] → 每次恢复先核验代数，不再读取或保存失效模型；定向验证首批提交后清理且旧任务不回填。
- [中途失败被最终保存成功掩盖] → 独立记录批次保存失败，使用一次失败后真实提交恢复的回归验证水位与事件。
- [本地输入被迟到响应覆盖] → 在首批提交后修改稍后将处理的训练，验证待推送标记、输入及原子树身份保留。
- [单棵树或已有记录更新仍过重] → 完整聚合不截断，补充长训练及已有子树更新场景，保留尚未通过的性能项。

## Migration Plan

没有数据迁移、后端重启或部署需求。iOS 编译、定向可靠性回归和同口径性能复核后进入专项后续门禁；回滚只撤销本地执行策略，既有数据、同步字段和协议不变。
